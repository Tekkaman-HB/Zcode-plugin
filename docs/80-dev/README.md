# 80-dev — 目标说明

## 目标

存放编码过程中临时产生的问题分析、排障记录、实施方案和验证记录，作为当日工作的可追溯草稿区。

## 放什么

带日期的问题分析、临时方案、验证记录、未完全定稿但需要保留上下文的开发过程文档。

## 不放什么

- 已确认且影响系统边界、数据模型、接口契约、部署/运行拓扑或核心流程的结论 → 当日收尾抽取到 20-architecture/（必要时 ADR）
- 长期有效的开发规范、命令、工程实践和 AI 工作规则 → 30-engineering/
- 路线图、阶段计划、正式变更记录 → 50-planning/
- 已完成或废弃的历史方案 → 经收敛确认后移入 99-archive/

## 命名格式

严格使用 `YYYY-MM-DD-中文主题.md`，例如：`2026-09-28-权限卡重发去重方案.md`。

- 日期使用文件创建或对应工作的日期，固定为四位年、两位月、两位日。
- 日期后紧跟一个 `-`，不得加空格；文件名部分不得为空。
- 整个文件名不得含空格；主题以清晰中文描述为主，可保留 `Context`、API 等必要技术术语。
- `README.md` 是通用入口，不应用日期前缀。

## 内容格式

frontmatter 至少包含 `status: active` 和 `owner`，正文只有一个一级标题，并至少包含：

- `## 问题与目标`：说明问题、建议或想法，以及希望达到的结果。
- `## 当前实际情况`：记录现象、证据和影响，明确区分事实与假设。
- `## 优化方案`：记录方案、实施/验证结果、待同步事实文档和剩余事项。

章节不加 `1.`、`2.` 等手工序号；需要补充内容时放在最接近的必需章节下。

## 编写要求

- 每份增量文档按三段式写明问题、事实、方案、验证、需要更新的事实文档和剩余事项。
- 允许记录过程，但必须标出“已验证结论”；不得把未验证猜测直接同步到事实目录。

## 与 30-engineering 的区别

`30-engineering/` 是稳定工程知识，回答「以后开发者应该怎么做」；`80-dev/` 是开发现场工作区，回答「今天为了解决某个具体问题分析了什么、试了什么、暂定什么」。`80-dev/` 中沉淀出可复用工程实践后，再抽取到 `30-engineering/`。

## 收尾规则

方案或阶段实施完成时主动判断是否可收敛，并先展示确认清单：完成证据、已验证事实、拟更新或新建的 `10-product/`、`20-architecture/`、`30-engineering/`、`40-operations/` 文件、冲突及拟移动源文件。用户确认后才按目标目录 README 更新事实并把清单中的源文件移动到 `99-archive/`；没有新事实时可仅归档。确认只覆盖清单范围，执行中新发现的文件、冲突或扩大项跳过并报告。日期前缀文件本地最后修改时间超过 7 天时轻量提醒。未明确要求 60/70 时当作不存在。
