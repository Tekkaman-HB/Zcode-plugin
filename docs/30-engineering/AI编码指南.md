# AI 编码指南

## Before Any Task

1. 读 AGENTS.md 与 docs/README.md。
2. 读 docs/00-context/硬约束.md（硬约束，不可违反）。
3. 改架构前读 docs/20-architecture/架构概览.md；改协议相关代码前读根 CLAUDE.md 的逆向结论（唯一事实源）。
4. 新建或更新非保护目录文档前先读目标目录的 README.md，按命名格式、内容格式和编写要求组织内容。
5. 涉及智能体/LLM 语义决策路径时，读 `docs/00-context/智能体边界规范.md` 与 `docs/20-architecture/智能体决策清单.md`；不存在但项目证据表明应启用时先报告规范缺失，不自行发明边界。

## 行为准则（写码四律）

> 面向 AI 与人的编码行为合同。四律整体偏向谨慎而非速度；琐碎任务可按判断放宽，但不得静默跳过验证。AGENTS.md 的 `Behavior` 段是本节的入口摘要，两处不一致时以本节为准并同步修正摘要。

### 1. 先想后写

- 实现前显式列出假设与前提；不确定就提问，不用猜测填充。
- 存在多种合理解释时全部摆出，请用户裁决，不静默选定其一。
- 发现更简单的可行方案必须说出来，必要时反驳当前方案。
- 遇到看不懂的需求或代码，停下来指出具体困惑点，不带着困惑硬写。

### 2. 简单优先

- 只实现被要求的功能；不为“未来可能需要”提前造轮子。
- 一次性代码不建抽象；不加未要求的灵活性、可配置性和选项开关。
- 不为不可能发生的场景写错误处理；防御性代码必须有真实触发路径。
- 写完自检“资深工程师会不会说这过度复杂”；200 行能压到 50 行就重写。

### 3. 外科手术式修改

- 只改与任务直接相关的代码；不顺手“改进”邻近代码、注释或格式。
- 不重构没坏的东西；匹配既有风格，即使与个人偏好不同。
- 发现无关的死代码或坏味道：报告，不擅自删除或修复。
- 只清理本次改动自己产生的孤儿 import / 变量 / 函数。
- 终检标准：diff 里每一行改动都能直接追溯到本次请求。

### 4. 目标驱动验证

- 把任务翻译成可验证目标再动手：“加校验”→“先写非法输入的测试并让其通过”；“修 bug”→“先写复现测试，再让它通过”；“重构 X”→“前后测试都保持绿”。
- 多步任务先列计划，每步带验证点：`1. 步骤 → verify: 检查方式`。
- 成功标准要强到能支撑自主循环到验证通过；只有“能跑就行”这类弱标准时，先向用户澄清验收口径再动手。

## Verification

- 代码改动：`npm run typecheck` + `npm run build`；UI 改动加 `npm run theme-check`；协议改动加 `npm run smoke`（⚠ 需登录态）。
- 文档改动：`npm run docs:check`。
- 每次代码变更走 GEB 回环：更新文件 L3 头部（INPUT/OUTPUT/POS）与所在目录 CLAUDE.md。

## Boundaries

- 只改与任务相关的代码，不顺手重构。
- 不引入未经 ADR 批准的新技术。
- 重大架构决策必须新增 ADR。
- 业务文档默认使用中文文件名；通用/生态固定文件保持约定名。
- 临时实施分析放 `docs/80-dev/`，严格使用 `YYYY-MM-DD-中文主题.md`，正文使用「问题与目标 / 当前实际情况 / 优化方案」三段式；临时阶段计划放 `docs/50-planning/` 并使用日期前缀。
- 完成 50/80 中记录的方案或阶段时主动判断是否可收敛；先展示完成证据、已验证事实、10/20/30/40 目标、冲突和拟移动源文件，用户确认后才按目标目录 README 更新事实并移动清单中的源文件。
- 50/80 日期前缀文件的本地最后修改时间超过 7 天时轻量提醒考虑收敛；不维护额外提醒状态。
- 未经用户明确授权，所有搜索、扫描和链接核查都显式排除 `docs/60-marketing/`、`docs/70-research/`、`docs/99-archive/`。未明确要求 60/70 时当作不存在。
- `docs/99-archive/` 默认不读取、不维护；用户确认收敛清单后仅可读取本次移动所需的说明和目标位置，已有或无关归档文件不得自动更新、整理、重命名或删除。

## Review Checklist（完成任务前自检）

- [ ] 开工前列出了假设与方案取舍，没有静默二选一？
- [ ] 只实现了被要求的功能，没有投机抽象或未要求的灵活性？
- [ ] diff 里每一行改动都能追溯到本次请求，没有顺手改无关代码？
- [ ] 任务有可验证的成功标准，并在交付前验证通过？
- [ ] 改了架构，是否补了 ADR？
- [ ] 改了硬约束，是否更新 `硬约束.md`？
- [ ] 协议相关改动是否核对了根 CLAUDE.md 的逆向结论，没有凭记忆改协议行为？
- [ ] 代码变更是否完成 GEB 回环（L3 头部 + 目录 CLAUDE.md）？
- [ ] 新增/更新文档是否符合目标目录 README 的编写要求，而不是流水账？
- [ ] 新增业务文档是否使用中文文件名？
- [ ] 新增 `80-dev/` 文件是否使用无空格的 `YYYY-MM-DD-中文主题.md`，且包含三段式必需标题？
- [ ] 新增 `50-planning/` 临时计划是否使用日期前缀？
- [ ] 若 50/80 中对应方案或阶段已实施完成，是否先展示了完成证据、已验证事实、10/20/30/40 目标、冲突和拟移动源文件？
- [ ] 是否等待用户确认后，才更新事实并移动清单中的源文件？
- [ ] 是否在未获授权时避开了 60/70 的读取与更新？
- [ ] 是否只处理确认清单范围，并跳过执行中新发现项？
- [ ] 跑通项目原生测试命令与 docs 校验命令？
